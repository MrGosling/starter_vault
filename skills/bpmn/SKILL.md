# /bpmn - файл BPMN 2.0 для Camunda из сырых данных

Результат - один файл `.bpmn`, который открывается в Camunda Modeler без правок и показывает схему.

## Вход

- Сырьё: путь к файлу (`inbox/`, `effort/`) или текст в сообщении. Это может быть протокол, описание шагов или CSV-экспорт Frappe Workflow. Входа нет - попроси путь и остановись.
- Версия Camunda: 7 или 8. Бери из запроса или из `Стек и окружение.md`. Не названа - задай один вопрос и остановись: от версии зависят пространства имён, атрибуты и язык условий.
- Для имён ролей, состояний и статусов сверяйся с `Справка о системе.md`.

## Не додумывай

- Шаги, роли, условия и названия берёт только из источника. Нет в источнике - не придумывай шаг. Элемент с пробелом пометь `<bpmn:documentation>уточнить: что именно</bpmn:documentation>`.
- Названия в `name` - дословно из источника, не переформулируй.
- Данные обезличены. ФИО, логины и почты из сырья в файл не переноси: заменяй ролью или пропускай.
- Дорожки (lanes) не строй, пока не попросили. Роль кладётся в атрибут назначения задачи.

## Как собирать

1. Прочитай сырьё и выпиши для себя: старт, шаги, кто выполняет, развилки с названиями действий, концы. Неясные места - в список «уточнить».
2. Сгенерируй XML скриптом на Python во временной папке сессии, а не руками. Руками модель ошибается в координатах и ссылках. Файл записывай инструментом Write, а не через `cat <<EOF`.
3. Структура файла: `bpmn:definitions` (пространства имён `bpmn`, `bpmndi`, `dc`, `di`, `xsi` и платформы), один `bpmn:process`, затем `bpmndi:BPMNDiagram`. Без блока `bpmndi` Modeler откроет пустое поле, поэтому у каждого узла должен быть `BPMNShape`, а у каждого потока - `BPMNEdge`.
4. Идентификаторы: уникальные, начинаются с буквы (`Task_1`, `Flow_1`), без пробелов. Кириллицу держи в `name`, а не в `id`.
5. Раскладка: уровни по обходу в ширину от старта, слева направо. x = 100 + уровень * 180, ветки в одном уровне - со сдвигом по y на 120. Размеры: событие 36x36, задача 100x80, шлюз 50x50. Поток идёт от правой середины источника к левой середине цели. Возвратные потоки (на доработку) обводи снизу через промежуточные точки.

### Camunda 7

- Пространство имён `xmlns:camunda="http://camunda.org/schema/1.0/bpmn"`, у процесса `isExecutable="true"`.
- Если версия 7.20 и выше, спроси или задай `camunda:historyTimeToLive`: без него развёртывание может не пройти.
- Задача человека: `bpmn:userTask` с `camunda:candidateGroups="роль1,роль2"`. Автоматический шаг: `bpmn:serviceTask`.
- Условия на потоках из эксклюзивного шлюза: `bpmn:conditionExpression xsi:type="bpmn:tFormalExpression"` со значением вида `${action == 'Одобрено'}`.

### Camunda 8

- Пространства имён `xmlns:zeebe="http://camunda.org/schema/zeebe/1.0"` и `xmlns:modeler="http://camunda.org/schema/modeler/1.0"`, у definitions `modeler:executionPlatform="Camunda Cloud"`, версию платформы бери из запроса.
- Задача человека: `bpmn:userTask` с `zeebe:assignmentDefinition candidateGroups=...` внутри `extensionElements`. Автоматический шаг: `bpmn:serviceTask` с `zeebe:taskDefinition type=...`; тип задачи не придумывай, ставь `уточнить`.
- Условия на потоках - выражения FEEL, начинаются с `=`, например `= action = "Одобрено"`.

- В обеих версиях переменная условий называется `action`, её значение - название действия из источника. Это принятое соглашение, упомяни его в ответе одной строкой.
- В атрибутах Camunda не уверен - не угадывай, оставь `уточнить`.

## Экспорт Frappe Workflow (CSV)

Строка CSV с `Document Type` - заголовок workflow. Таблицы состояний и переходов лежат в соседних строках, пустые ячейки означают продолжение. Правила перевода:

| Во Frappe | В BPMN |
|---|---|
| Первое состояние | Старт и задача этого состояния |
| Состояние, из которого есть переходы | `userTask`, `name` = название состояния; роли из `Allowed` его переходов - в назначение задачи |
| Несколько переходов из состояния | Эксклюзивный шлюз после задачи, потоки названы по `Action` |
| `Next State` | Поток к задаче этого состояния |
| Состояние без исходящих переходов | `endEvent` с тем же `name` |
| `Condition` (Python) | В условия не переводится, пишется в `documentation` потока как есть |
| `Allow Self Approval`, `Allow Edit` | В `documentation` задачи |

Переход «из состояния в себя» и циклы (возврат на доработку) сохраняй как есть, возвратные потоки обводи снизу.

## Проверка перед ответом

Скриптом проверь: XML читается (`xml.etree.ElementTree`), все `id` уникальны, каждый `sourceRef` и `targetRef` указывает на существующий элемент, у каждого узла есть `BPMNShape`, у каждого потока - `BPMNEdge`, у каждого шлюза с несколькими выходами названы и снабжены условием все выходы, на старте нет входящих, на концах нет исходящих. Не прошло - исправь и проверь снова.

## Куда класть и что отвечать

- Файл: `effort/<тема>/<имя процесса>.bpmn`. Тема из запроса, нет - рядом с исходником, если он в `effort/`. В `clippings/` не пиши, там запись запрещена.
- Исходник не меняй и не удаляй.
- Ответ короткий: путь к файлу, версия Camunda, число задач, шлюзов и событий, список «уточнить» не длиннее пяти строк. XML в чат не выводи.
