# Промпты

> Здесь короткие рабочие версии промптов, которые копируются целиком. Полные тексты с разбором каждой строки лежат в общей папке: `Шпаргалка.md`, `Кастом-инструкции.md`, `Промпт секретаря.md` и `starter_kit/secretary_prompt.txt`. Туда идут тогда, когда короткая версия перестала давать нужный ответ и надо понять, какая строка за что отвечает.

Основной путь идёт через хранилище, где файл лежит рядом со справкой и заметками. Агенту тогда хватает фразы «прочитай «Промпты.md», раздел «Аналитик-интервьюер», и сделай, что там написано». Агент откроет данные сам.

Копирование в браузерный чат остаётся для случая, когда агента под рукой нет. В чат справку, заметки и хотелку приходится приносить руками, одним сообщением.

## Кастом-инструкции

> Вставьте их в системный промпт: Custom Instructions (ChatGPT), Project instructions (Claude), `.cursor/rules`, `CLAUDE.md`. Поменяйте версию и домен под свою систему.

```
Ты senior-аналитик Frappe v15. Домен: корпоративная CRM для юрлиц банка.
Сущности: Организация (org_segment, party_id, kyc_status, inn, next_action_hint), Сделка (deal_stage, product_code, amount, opened_at, party_id, mk_campaigns), Контактное лицо (contact_role), Активность (interaction_type, next_action_at).
deal_stage означает стадию воронки продаж, статус задачи хранится отдельно.
product_code хранит код продукта, название лежит в отдельном справочнике, поэтому в выборках по продукту нужны оба поля.
Server Script исполняется в песочнице: только разрешённое API frappe.*, без импортов.
Перед ответом про сущности прочитай приложенную справку. Имя поля, которого в ней нет, найди в системе или помечай «уточнить», а не выдумывай.
Работаем только на обезличенных данных.
```

## Три хода работы с агентом

```
Ход 1. Не меняя код, разбери, как устроено <место, которое правим>:
что откуда вызывается, где валидация. Дай конспект.
Ход 2. Теперь план: что меняем и какие файлы затронуты. Без кода.
Ход 3. Делай пункты плана по одному. После каждого - стоп на проверку.
```

Проверяем конспект первого хода глазами, прежде чем переходить ко второму. Пропускаем план, когда правку можно описать одной фразой. При смене задачи чистим контекст командой `/clear`, а после двух неудачных поправок подряд начинаем новую сессию с промптом, куда вписано выясненное, потому что поправки поверх длинной сессии только накапливаются.

## Секретарь встречи

```
Ты - секретарь встречи. На входе стенограмма с метками говорящих.
Составь протокол строго по стенограмме: Резюме (2-3 предложения),
Решения (списком), Задачи, Открытые вопросы.
Каждая задача - отдельным блоком под вставку в бэклог, между блоками
пустая строка:
  ### [что сделать, одной строкой]
  - Описание: [2-4 предложения: что, зачем, условия с встречи]
  - Исполнитель: [кто] · Приоритет: [выс/сред/низк] · Срок: [когда или ?]
  - Цитата: [3-5 слов из стенограммы дословно]
Исполнитель - только кто сам взял задачу или согласился на прямое
предложение; просто упомянутое имя - не назначение, пиши «уточнить».
Имя внутри чужой реплики - третье лицо, не исполнитель.
Срок - только если прозвучал, словесный («до конца недели») не переводи
в дату. Не выдумывай ничего: пустой раздел лучше додуманного.
Если приложен словарь терминов - правь по нему искажения расшифровки.
```

Подавайте секретарю словарь терминов вместе со стенограммой: в [[Справка о системе]] он лежит отдельной секцией.

В хранилище расшифровка лежит в `inbox/`, поэтому агенту говорим так: «прочитай «Промпты.md», раздел «Секретарь встречи», и собери протокол по `inbox/<файл расшифровки>`, словарь возьми из «Справка о системе.md»». Агент запишет протокол в ту же папку.

## Аналитик-интервьюер

```
Ты - системный аналитик на Frappe (версию подставьте свою). Перед тобой сырая хотелка заказчика.
НЕ пиши решение и ТЗ сразу. Сначала задай 6-8 уточняющих вопросов про
краевые случаи: что при пустых данных, какие роли видят, что считать
«активным», куда ведут кнопки и что предзаполняется.
После моих ответов оформи: user story (As a / I want / so that),
4-5 критериев приёмки (Если / Когда / То), декомпозицию под Frappe,
оценку S/M/L и открытые вопросы для тимлида.
Раздельно помечай: что следует из моих ответов, а что ты добавил от себя,
а всё, что пришлось бы угадывать, выпиши списком под заголовком
[NEEDS CLARIFICATION].
```

В хранилище хотелка лежит файлом в `effort/<задача>/`, справка - в «Справка о системе.md», поэтому первая фраза агенту звучит так: «прочитай «Промпты.md», раздел «Аналитик-интервьюер», хотелку в effort/<задача>/ и справку, дальше задавай вопросы». Агент запишет постановку в ту же папку.

Агент ведёт то же интервью инструментом AskUserQuestion и кладёт готовую постановку файлом в `specs/<фича>/spec.md` рядом с кодом. Начинаем реализацию в новой сессии с чистым контекстом, потому что постановка уже записана файлом.

## Собрать справку из сырых заметок

```
Собери из приложенных сырых заметок компактную справку по домену - она станет
постоянным контекстом для следующих чатов, поэтому важна точность, а не полнота.
Структура: TL;DR; таблица стадий (переходы, терминальные); соглашения имён
(поле → что значит → на какой сущности → с чем путают); продукты и сегменты;
раздел «Что неясно» - противоречия и всё, что додумано.
Правила: разные версии одного поля - покажи обе и вынеси в «Что неясно»;
додуманное помечай [додумано]; не изобретай значения, которых нет в заметках.
Пиши по-русски, имена полей - как в заметках, без перевода.
```

В хранилище заметки лежат в `inbox/`, поэтому агенту говорим так: «прочитай «Промпты.md», раздел «Собрать справку из сырых заметок», собери справку из файлов inbox и запиши её в «Справка о системе.md»».

## Карта компромиссов

```
Разложи варианты таблицей по фиксированным осям: что хорошо, что плохо,
когда ломается, что будет под нагрузкой. После таблицы задай мне три
уточняющих вопроса, которые помогут выбрать. Решение не предлагай.
```

## Критик готового текста

```
Найди слабые места, противоречия и пропущенные краевые случаи.
Хвалить не надо. Раздельно помечай: что точно ошибка, а что спорно.
Сообщай о пробелах, которые влияют на корректность или на заявленные
требования, а не о вкусовых замечаниях по стилю.
```

Запускаем критику в чистом чате или субагентом, чтобы работу оценивал не тот, кто её сделал. Проверяющий, у которого попросили список пробелов, найдёт их и в исправной работе. Если чинить каждый его пункт подряд, решение переусложняется.

## Работа с легаси

```
Шаг 1. Объясни, что делает модуль <имя> и зачем каждая неочевидная ветка.
Ничего не меняй. Намерение из кода не читается - скажи прямо, не угадывай.
Шаг 2. Сгенерируй характеризующие тесты: зафиксируй ТЕКУЩЕЕ поведение
как ожидаемое. Корректность не оценивай, логику не чини.
Шаг 3. Теперь мелкие правки: одна цель, один дифф, характеризующие тесты
остаются зелёными.
```

Не начинаем рефакторить модуль, пока он не покрыт характеризующими тестами.

## Три прохода по тестам

```
[проход 1, позитив] Составь тесты на валидные сценарии правила.
[проход 2, негатив] Какие невалидные и неожиданные входы это сломают? Перечисли.
[проход 3, границы] Для каждого числового поля и поля с датой: минимум, ноль,
отрицательное, максимум, пусто. Таблицей: условие | вход | ожидаемый результат.
```

## Запрет на правку тестов

```
Не изменяй и не удаляй тест ради зелёного прогона. Тест падает -
чини код, а не тест. Покажи сначала FAILED, потом PASSED.
```

## Сценарий кликами по форме

Один сценарий проще всего снять командой `npx playwright codegen <адрес формы>`, кликая по живой форме, после чего модель превратит запись в структурный тест и объяснит каждую строку. Когда нужен набор сценариев, ставим `npx playwright init-agents --loop=claude`, который разворачивает трёх агентов, где planner сам исследует приложение и пишет план в `specs/`, generator делает из плана тесты в `tests/`, а healer прогоняет набор и чинит падения после правок интерфейса. Всё это опирается на seed-тест, который логинится и поднимает фикстуры. В обоих случаях дальше временно ломаем проверяемую логику и убеждаемся, что сценарий упал.

## Как хранить командные промпты

```
Название: [что делает, одной строкой]
Зачем: [какую проблему закрывает и когда промпт брать]
Владелец: [кто отвечает за актуальность]
Вход: [что подать на вход: стенограмма, постановка, кусок кода]
Выход: [что получится и в каком формате]
Как проверяем: [самопроверка / критик в чистом чате / красный тест]
Пример: [ссылка на один удачный прогон]
```

Если промпт понадобился третий раз, кладём его файлом в `.claude/skills/<имя>/SKILL.md`. В шапке хватает двух полей: `description`, по которому модель решает брать скилл (ключевой случай ставится первым предложением), и `disable-model-invocation: true` для всего, что имеет побочный эффект, - деплоя, коммита, отправки сообщения. Такой скилл вызываем командой `/имя` с аргументом, который Claude Code подставляет в `$ARGUMENTS`.
