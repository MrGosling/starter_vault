## TL;DR

ITSM-система коммерческого банка на Frappe Framework v16.
Сущности: Пользователь, Сотрудник, Система, Сеть, Узел, Обращение в техподдержку, Заявка на доступ.
В системе работают все сотрудники банка. Сотрудники департамента информационных технологий - админы и пользователи (наполнение системы, обработка обращений). Остальные сотрудники - пользователи (создают обращения, запрашивают доступы).

Три базовые сущности Frappe, на которых всё держится:
- **DocType** описывает модель: поля, права, таблицу БД, форму и REST-эндпоинт.
- **User** - учётная запись. Права даёт не сам пользователь, а его роли.
- **Workflow** - конечный автомат статусов поверх одного DocType. Меняет `docstatus` и своё поле состояния по переходам, разрешённым ролям.

## Сущности и стадии

Бизнес-запись - это **Document** (экземпляр DocType), у неё две независимые оси состояния: `docstatus` (техническая) и поле workflow (бизнес-стадия). Из Submitted (1) в Draft (0) вернуться нельзя, только Cancel (2) и Amend.

| Сущность | Ключевые поля | Стадии/статусы |
|---|---|---|
| DocType | `name`, `module`, `fields`, `permissions`, `istable`, `issingle`, `is_submittable`, `autoname` | Не документ процесса, стадий нет |
| User | `name` (= email), `email`, `full_name`, `enabled`, `user_type`, `roles` (таблица Has Role) | `enabled` 0/1. `user_type`: System User (Desk) или Website User (портал) |
| Role | `role_name`, `desk_access` | Нет |
| Workflow | `document_type`, `workflow_state_field` (по умолчанию `workflow_state`), `is_active`, `states`, `transitions` | `is_active` 0/1. На один DocType активным может быть один workflow |
| Workflow Document State | `state`, `doc_status` (0/1/2), `allow_edit` (роль), `update_field`, `update_value` | Строка в `states` workflow |
| Workflow Transition | `state` → `action` → `next_state`, `allowed` (роль), `condition`, `allow_self_approval` | Строка в `transitions` workflow |
| Workflow Action | Задача на согласование для роли или пользователя, создаётся при переходе | Open / Completed |

| Сотрудник | Стандартный `Employee` (на него ссылается `Remote Access Request.employee`). Есть ли кастомные поля - уточнить | уточнить |
| Система | уточнить | уточнить |
| Сеть | уточнить | уточнить |
| Узел | уточнить | уточнить |
| Обращение в техподдержку | уточнить (свой DocType или Issue?) | уточнить, есть ли workflow |
| Заявка на доступ | уточнить (возможно, это `Remote Access Request` ниже, или отдельный DocType) | уточнить |

### Remote Access Request

Источник - экспорт DocType (`modified` 2026-07-20). Не submittable и не дочерняя таблица. Имя записи `AR-{employee}-{######}`, включены `track_changes` и `track_seen`.

- **Для кого**: `employee` (Link → Employee, обязательное, есть в списке и фильтрах). `phone_no` - редактируемый телефон.
- **Данные из AD** (скрыты, только чтение): `department`, `designation`, `branch`.
- **Данные из 1С** (только чтение): `division_1c`, `position_1c`, `territory_1c`.
- **Параметры доступа** (все обязательные): `time_to_access` (6 временных планов от «09.00-18.00(обычный)» до «24часа(круглосуточный)»), `date_start`, `date_end` (включительно), `reason`.
- **Рабочее место** (все обязательные): `workstation` (АРМ), `workstation_type` (Стационарная, Ноутбук, Планшет), `operating_system` (Windows, MacOS, Linux, Android, Иная), `defender_name` (средство защиты от вредоносного ПО).
- **Контакты** (обязательные): `private_phone_no` (экстренная связь), `private_email`.
- **Согласие по ИБ**: `security_agreement` (текст, только чтение), `security_agreement_acceptance` (Check, не обязательное).
- **Служебные**: `sort_order` (кнопка, скрыта в «Новая заявка»), `state_machine_log` (виртуальное HTML-поле «State Machine»).

Значения `status` (поле Select, только чтение, порядок как в JSON; переходы между ними в JSON не описаны): Новая заявка, Черновик, На доработке, Согласование руководителя, Отклонено руководителем, Согласование УИБ, Отклонено УИБ, Исполнение заявки, Доступы предоставлены, Отклонено техническим специалистом, Доступы отозваны, Отклонено.

Права на DocType (у всех также email, export, print, report, share; submit и cancel ни у кого нет):

| Роль | Чтение | Создание | Запись | Удаление |
|---|---|---|---|---|
| System Manager | да | да | да | да |
| ITSM Manager | да | да | да | да |
| Technical support | да | да | да | нет |
| ITSM User | да | да | да | нет |
| Access Requestor | да | да | да | нет |
| All (все пользователи) | да | нет | нет | нет |

## Соглашения имён

| Поле | Что означает | С чем путают |
|---|---|---|
| `docstatus` | Техническое состояние записи: 0 Draft, 1 Submitted, 2 Cancelled | `workflow_state`, `status`. Это бизнес-стадия, у неё свои значения и она не равна docstatus |
| `workflow_state` | Поле с текущим состоянием workflow. Имя настраивается в `workflow_state_field` | `status`. Так называют своё поле во многих DocType, но оно не управляется workflow |
| `name` | Первичный ключ записи. Для User - email | `title`, `full_name`. Это отображаемые подписи, а не ключи |
| DocType | Описание модели (класс) | Document. Это одна запись (экземпляр), хранится в таблице `tab<DocType>` |
| Role | Набор прав на DocType | User Permission. Он ограничивает по значениям Link-полей, а не даёт права |
| `permlevel` | Уровень доступа к полю внутри DocType | Уровень роли или должности. К иерархии пользователей отношения не имеет |
| `enabled` | Учётка пользователя включена | `user_type`. Он определяет Desk или портал, а не активность |
| `owner` (Remote Access Request) | Пользователь, создавший заявку | `employee`. Это сотрудник, для которого запрашивают доступ, и он не обязан совпадать с автором |
| `department`, `designation`, `branch` (заявка) | Подразделение, должность, филиал **из AD**, скрытые поля | `division_1c`, `position_1c`, `territory_1c`. Это те же понятия **из 1С**, у них подписи «Подразделение», «Должность», «Филиал» без «AD» |
| `time_to_access` | Временной план: в какие часы суток разрешён доступ | `date_start`, `date_end`. Они задают срок действия в днях |
| `status` (заявка) | Бизнес-статус заявки, обычное поле Select | `docstatus`. Он технический (0/1/2) и у этой заявки не используется |

## Правила домена

- Права собираются из четырёх слоёв: Role Permission на DocType (с `permlevel`), User Permission (ограничение по значениям Link), DocShare (доступ к конкретной записи) и условия в workflow. Если пользователь не видит запись, проверять надо все четыре.
- В workflow переход меняет `docstatus` только вперёд: 0 → 1 → 2. Возврат из Submitted в Draft не делается переходом.
- Редактировать запись в состоянии можно только роли из `allow_edit` этого состояния. Запись с `docstatus` 1 не редактируется, кроме полей с `allow_on_submit`.
- `Administrator` обходит проверки прав, `Guest` - анонимный пользователь. Поведение прав проверяем под обычной ролью, а не под Administrator.
- Переход выполняет роль из `allowed`. Если нужно ограничить условием, оно пишется в `condition` как Python-выражение, а `allow_self_approval` решает, может ли автор сам утвердить свою запись.
- Банковское правило: уточнить, какие сущности ITSM требуют согласования и какие роли их согласуют.
- Заявка на удалённый доступ меняется только в статусах «Новая заявка» и «На доработке» (Administrator - в любом). Это условие `read_only_depends_on` в форме, то есть проверка на клиенте. Защищает ли от правки сервер - уточнить.
- `private_phone_no` и `private_email` в форме видят Administrator, роли Officer of Information Security и Head of Information Security и автор заявки (`doc.owner`). Это `depends_on`, то есть только клиент, `permlevel` у полей нет. Роль All читает DocType целиком, поэтому через API эти поля могут быть доступны всем. Проверить.
- Перед предоставлением доступа заявка, судя по названиям статусов, проходит руководителя, затем УИБ, затем исполнение. Реальные переходы и роли - уточнить.

## Что неясно

- [ ] Какие из сущностей ITSM (Система, Сеть, Узел, Обращение, Заявка на доступ) - свои DocType, а какие - стандартные (например, Issue). Сотрудник - это Employee, подтверждено.
- [ ] «Заявка на доступ» из списка сущностей - это `Remote Access Request` или отдельный DocType.
- [ ] Для каких DocType уже настроены workflow, какие у них состояния, переходы и роли. У `Remote Access Request` есть virtual-поле «State Machine»: возможно, переходами управляет код, а не DocType Workflow.
- [ ] Список ролей системы. Известны: System Manager, ITSM Manager, ITSM User, Technical support, Access Requestor, Officer of Information Security, Head of Information Security, All. Как они делятся на админов и пользователей департамента ИТ - уточнить.
- [ ] `Remote Access Request.reason`: у поля тип Small Text, но заданы options «Первичное трудоустройство, Перевод, Новый функционал». Для Small Text options не работают, возможно, поле должно быть Select.
- [ ] `security_agreement_acceptance` не обязательное: можно ли передать заявку дальше без согласия, проверяется ли это в коде.
- [ ] Есть ли в системе User Permission и по каким DocType они ограничивают данные.
